# tools/dbfn_sites.txt -- AUTHORITATIVE -fno-delayed-branch signature-site list
# wave-25 agent a9 (THE SURVEYOR), Task 1. Built by mechanically scanning every oracle
# asm/nonmatchings/main/*.s (2563 files) for the PsyQ-syslib -fno-delayed-branch
# epilogue fingerprint, then validating EVERY hit against the live verify_asm.py gate
# (a hit only counts if the CURRENT recon, built with normal/standard flags, actually
# FAILs with the tell-tale epilogue-swap diff -- see METHODOLOGY below).
#
# METHODOLOGY (full detail: memory reference_psx_cpp_reconstruction_methodology.md
# section 3.25 axis 3b -- "DELAYED-BRANCH FILLING identity"):
#
# Sony built PsyQ 4.3's syslib with gcc's OWN delay-slot filling OFF
# (-fno-delayed-branch); the real ASPSX assembler then filled branch/load delay slots
# itself, mechanically. Its epilogue filler could NOT move the frame-deallocation
# "addiu $sp,$sp,+N" into the final "jr $ra"'s own branch-delay slot (that slot is a
# SEPARATE physical instruction from whatever filled the preceding "lw $ra"'s load-delay
# slot -- the same addiu instruction cannot occupy two delay slots at two different
# addresses), so the tail is always: "... ; addiu $sp,$sp,+N ; jr $ra ; nop".
# A NORMAL (delayed-branch-ON) gcc build, by contrast, has full freedom to reorder the
# independent, no-side-effect "addiu $sp,$sp,+N" directly INTO the "jr $ra" delay slot
# ("... ; jr $ra ; addiu $sp,$sp,+N") since nothing stops that swap -- this is the single
# most common PSX epilogue idiom in ordinary (game/EA) code.
#
# FINGERPRINT (the only one that survived false-positive testing):
#   EPI:  "addiu $sp,$sp,+N" immediately followed by "jr $ra" immediately followed by
#         "nop", found ANYWHERE in the epilogue tail (s-reg restore loads may legally
#         intervene between "lw $ra" and this addiu -- PCread/PCwrite are real dbfn
#         sites but were only caught once the pattern was generalized past strict
#         adjacency to "lw $ra").
#   EPI-adjacent: the stricter original w23-style form, "lw $ra,N($sp)" DIRECTLY
#         followed by "addiu $sp,$sp,+N" DIRECTLY followed by "jr $ra" DIRECTLY followed
#         by "nop" -- a subset of EPI (71 of the 76 sites below; this subset alone
#         happens to reproduce the historical w23 "~71 sites" estimate almost exactly,
#         which appears to have been exactly this stricter pattern, under-counting the
#         5 non-adjacent sites: PCread, PCwrite, PAD_restore, PAD_update, padinit).
#
# REJECTED as a fingerprint -- "FP2" PROLOGUE PATTERN ("addiu $sp,$sp,-N" ; "sw $ra,M($sp)"
# ; "jal X" ; "nop"): this looked plausible by analogy but is a FALSE-POSITIVE MAGNET --
# 88 raw hits, ~90% of them ordinary GAME C++ (AIHigh_*/AIDataRecord_* destructors,
# BWorld_*, AITune_*, etc; also flagged libsn's OWN __builtin_delete/__builtin_vec_delete,
# manually confirmed NEGATIVE -- their real epilogue is the normal "lw ra;nop;jr ra;addiu
# sp" filled form). The jal-delay-slot nop is architecturally FORCED regardless of compile
# flags: "$ra" can never be saved into the very first "jal"'s own delay slot since the jal
# concurrently overwrites $ra, so ANY trivial single-call wrapper -- delayed-branch-ON or
# OFF -- shows a nop there. Not included below; not a valid discriminator.
#
# ALSO EXCLUDED (investigated + confirmed FALSE POSITIVE of the EPI pattern itself):
#   AI_KeepCarsInLane__FP8Car_tObj (recon/game/common/ai.cpp:1583, real GAME code) --
#   a fully-empty 4-insn body ("addiu sp,-0x10; addiu sp,0x10; jr ra; nop", a dead
#   "int local[4]" stack reservation with nothing to schedule) textually matches EPI but
#   verify_asm.py shows it ALREADY PASSES under STANDARD (delayed-branch-ON) build
#   flags -- i.e. gcc's own scheduler ALSO leaves that jr's slot nop when a function body
#   is completely empty, independent of -fno-delayed-branch. Proof that EPI hits must be
#   cross-checked against the live gate (PASS => reject) before counting a site.
#
# UNOWNED FINDING (flagged per task instructions -- real, if modest, news):
#   recon/eaclib/psx/pad.c (PAD.OBJ) carries 4 EPI sites: PAD_state, PAD_restore,
#   PAD_update, padinit. This is EA's eaclib layer, textually outside every wave-25
#   syslib-agent's scope (a2-a9) AND outside true "game" code -- but it is NOT surprising
#   EA game logic: pad.c is EA's thin wrapper directly over PsyQ libpad (same family as
#   the syslib PAD* sites a5 owns), and a PRE-EXISTING code comment at
#   recon/eaclib/psx/pad.c (right before PAD_state, added by a prior wave) already
#   documents the identical residual: "oracle has EVERY delay slot as a nop ...
#   reproduced exactly by cc1 -fno-delayed-branch, NOT by repo -O2/-O1 ... needs a

#   carries the syslib toolchain identity. NOT a case of ordinary EA-authored game C++
